# 工具编排与执行纪律

> 先判依赖，再判安全，最后才判要不要并行。

## orch.dependency_graph — 并行只在无依赖时

**何时适用**：一次要发起多个工具调用。

**步骤**

1. 写出调用间的数据依赖：谁的输出是谁的输入。
2. 无依赖 → 并行；有依赖 → 串行，且后者参数必须来自前者实测输出。
3. 写操作默认串行（文件、注册表、外部副作用）。
4. 并行调用必须有各自的超时与失败隔离。

**硬约束**

- 不得在未读取前一步结果时假定其输出。
- 同一资源的并发写一律禁止。

**验收门**

- `G-ORCH-DEP`：每个并行分支都能说明它不依赖其他分支的输出。
- 判失败：后一步用了前一步'预期'的结果而非实际结果。

**反例（真实踩过的坑）**

- 并行跑两个都要写同一文件的脚本，后写覆盖前写。
- 把上一步的假设参数直接喂给下一步。

## orch.gate_order — 安全门前置于审批门

**何时适用**：设计或审计任何执行链路。

**步骤**

1. 固定门序：参数校验 → 规模限制 → 路径/注入检查 → 权限与安全审计 → 人工审批 → 派发。
2. 确认'拦截'类门在'待批准'之前，否则攻击会被降级为'等一个批准'。
3. 每条门失败必须返回可区分的 verdict_code。
4. 为门序写一个攻击用例测试。

**硬约束**

- 审批门不得作为唯一防线。
- 不同失败原因不得共用同一个错误码。

**验收门**

- `G-ORCH-GATEORDER`：路径穿越/注入用例返回 BLOCKED 而非 APPROVAL_REQUIRED。
- 判失败：越权请求停在'待批准'状态。

**反例（真实踩过的坑）**

- out_root 指向系统目录却返回'需要审批'。
- 工具名拼错返回'需要授权'，误导用户去授权。

## orch.idempotent_retry — 重试必须幂等

**何时适用**：对失败步骤安排重试。

**步骤**

1. 分类动作：只读（可重试）/ 幂等写（可重试）/ 非幂等写（不可重试）。
2. 非幂等写要么加幂等键，要么先查状态再决定。
3. 重试加退避与上限，记录每次尝试。
4. 超限后上报，不静默放弃。

**硬约束**

- 非幂等动作禁止自动重试。
- 重试次数上限必须显式配置，不得无限循环。

**验收门**

- `G-ORCH-IDEMP`：每个可重试动作都标注了幂等性依据。
- 判失败：转账/下单/追加写被自动重试。

**反例（真实踩过的坑）**

- 上传失败重试三次，产生三份重复文件。
- 追加日志重试导致同一行出现两次。

## 输出契约

执行本族任一原子后，输出必须包含：所用原子 id、实际执行的检查、检查的原始输出（或摘要）、
以及 `measured` / `asserted` / `insufficient` 三档证据等级。无证据不得写 `measured`。
