# 代码阅读、修改与验证

> 最小 diff、改必有测、错必有证。

## code.read_before_write — 先读后改，最小 diff

**何时适用**：修改任何既有文件之前。

**步骤**

1. 读目标文件全文（不是片段），再读它的调用方与被调用方。
2. 确认现有约定：命名、错误处理、返回信封、日志格式。
3. 写 diff 前先用一句话说明'现在为什么会这样'。
4. 改动只覆盖必要行；顺手格式化/重命名拆成单独提交。
5. 改完自查：是否引入新的未使用导入、是否破坏旧调用方签名。

**硬约束**

- 未读全文不得替换函数体；不得凭文件名猜内容。
- 禁止用 'try/except: pass' 吞掉看不懂的异常来'修好'。

**验收门**

- `G-CODE-MINDIFF`：diff 行数与改动目标匹配，且每个被改函数都有调用方影响说明。
- 判失败：出现与任务无关的格式化噪声，或异常被静默吞掉。

**反例（真实踩过的坑）**

- 整文件重写导致历史逻辑丢失。
- 改了返回结构，调用方仍按旧字段取值，线上才炸。

## code.test_is_the_proof — 测试是唯一证据

**何时适用**：声称'已修复/已实现/可用'之前。

**步骤**

1. 先写能复现问题的最小用例（失败态）。
2. 改代码让它通过。
3. 补一条反例（旧 bug 的变体），确认不是只对样例生效。
4. 跑全量相关测试，记录条数与通过数。
5. 把命令与输出摘要贴进交付说明。

**硬约束**

- 没有失败→通过的转变，不算修复。
- 未跑测试不得写'已验证'；只能写'未验证'。

**验收门**

- `G-CODE-TEST`：存在复现用例、通过记录、回归结果三件套。
- 判失败：仅凭'代码看起来对'宣称完成。

**反例（真实踩过的坑）**

- 改完直接说'应该可以了'。
- 测试只覆盖 happy path，边界仍崩。

## code.bisect_not_guess — 二分定位，不猜

**何时适用**：出现异常、结果不符、行为漂移。

**步骤**

1. 保存完整错误：首个异常 + 栈顶业务帧 + 输入数据。
2. 二分输入空间（最小复现）或代码路径（注释/开关）。
3. 每轮只改一个变量，记录'改了什么→现象如何变'。
4. 定位到行后，解释因果链：输入→状态→错误分支。

**硬约束**

- 禁止同时改多处'试试看'。
- 现象消失但无法解释因果 = 未修复，只是被掩盖。

**验收门**

- `G-CODE-BISECT`：有最小复现 + 单变量变更日志 + 因果解释。
- 判失败：结论是'改了某处就好了'但说不清为什么。

**反例（真实踩过的坑）**

- 在 10 个地方加 print，靠感觉挑一个改。
- 偶发问题当作已解决，因为这次没复现。
