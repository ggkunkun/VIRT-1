# 任务分解与可验收规划

> 先定义'做完是什么样'，再决定第一步做什么。

## plan.decompose — 需求→可验收任务树

**何时适用**：需求是一句话、没有明确交付物清单时。

**步骤**

1. 写出 1 句交付物定义：谁在什么场景下拿到什么文件/链接/数值。
2. 倒推验收条件：3-6 条，每条必须能被第三方用命令或肉眼复核（含阈值）。
3. 按依赖切层：数据/环境 → 核心实现 → 校验 → 交付物。每层不超过一个可独立验证的产物。
4. 标出唯一的关键路径节点；其余节点允许并行。
5. 把不做的范围显式写出来（Out of scope），防止范围蔓延。

**硬约束**

- 验收条件里禁止出现'优化''完善''合理'等不可判定词。
- 任务树深度超过 3 层时，说明切分维度错了（按依赖切，不按文件切）。

**验收门**

- `G-PLAN-ACCEPT`：每条验收条件都能回答：用什么命令/看什么文件/阈值多少。
- 判失败：存在无法复核的验收条目，或交付物定义缺失。

**反例（真实踩过的坑）**

- 先写代码再想验收 → 做完发现方向错，返工成本最高。
- 任务树按'前端/后端/测试'切，实际依赖是串行的，导致并行全是空转。

## plan.probe_first — 先探针后承诺

**何时适用**：存在未验证的环境假设（依赖装不上、接口不通、模型不支持）时。

**步骤**

1. 列出所有'我以为成立'的假设，按推翻代价排序。
2. 对最贵的 1-2 条做最小探针：一条命令、一次调用、10 行脚本，只回答真假。
3. 把探针输出贴进计划，作为后续承诺的依据。
4. 探针失败 → 改方案，不是加大力度重试。

**硬约束**

- 未跑过探针的环境假设，不得写进承诺给用户的时间线。
- 探针必须留下可复现命令，不能只留结论。

**验收门**

- `G-PLAN-PROBE`：每个高风险假设都有一次实际执行的探针记录（命令 + 输出摘要）。
- 判失败：关键假设仍为'应该可以'。

**反例（真实踩过的坑）**

- 假设沙箱能装包，写了 500 行才发现 pip 被墙。
- 把'文档说支持'当成'本机可用'。

## plan.replan_not_retry — 失败后重规划而非重试

**何时适用**：同一动作连续失败 2 次，或错误信息与上次相同。

**步骤**

1. 停手，读完整错误（不是最后一行，是首个错误 + 调用栈根因）。
2. 判定失败类别：环境/权限、输入非法、逻辑错、外部不可用。
3. 只对'外部不可用'允许原样重试（且需退避）；其余三类必须改动作。
4. 把'改了什么'写进下一次尝试的记录，否则视为原地打转。

**硬约束**

- 相同命令 + 相同参数第 3 次执行 = 违规，必须解释为何仍可能成功。
- 禁止用'再试一次'掩盖未定位的根因。

**验收门**

- `G-PLAN-REPLAN`：失败后有明确的类别判定与动作变更记录。
- 判失败：连续两次尝试的命令与参数完全一致且无退避说明。

**反例（真实踩过的坑）**

- timeout 就加大 timeout，实际是死锁。
- 编码错误反复重跑，实际是文件本身是 UTF-16。

## 输出契约

执行本族任一原子后，输出必须包含：所用原子 id、实际执行的检查、检查的原始输出（或摘要）、
以及 `measured` / `asserted` / `insufficient` 三档证据等级。无证据不得写 `measured`。
